# Security (DevSecOps)

## Trivy container scanning: what it does and what the result means

> **Written explanation (for the submission form):**
> Trivy scans the two images built by the pipeline (`stockpilot-backend` and
> `stockpilot-frontend`). It checks the operating-system packages (Debian 13 in the
> Python image, Alpine 3.24 in the Nginx image) and the application libraries (the
> Python packages in the virtualenv, the npm-built assets) against public vulnerability
> databases. The pipeline prints a full report, then fails the build if any **HIGH or
> CRITICAL** vulnerability **with an available fix** is found, so a known-exploitable,
> patchable image can never reach GHCR or the cluster.
> Both images currently scan **clean (0 fixable HIGH/CRITICAL)**: no dependency has a
> known serious vulnerability that we could fix by upgrading.

**A finding we actually hit and fixed.** While choosing the backend base image, Trivy
reported 4 fixable HIGH vulnerabilities in `python:3.13-slim`, all in Python packages
bundled into that image, for example:

| Package | CVE / advisory | Fixed in | What it is |
|---------|----------------|----------|-----------|
| setuptools 70.3.0 | CVE-2025-47273 | 78.1.1 | path traversal: a crafted package can write files outside the target directory during install |
| urllib3 2.7.0 | CVE-2026-97687 | 2.8.0 | traffic interception via HTTPS-proxy TLS configuration override |
| urllib3 2.7.0 | CVE-2026-97689 | 2.8.0 | denial of service through unbounded memory allocation in the chunk parser |
| msgpack 1.1.2 | GHSA-6v7p-g79w-8964 | 1.2.1 | out-of-bounds read / crash |

`python:3.12-slim` had none, so the backend uses 3.12. Our gate would have blocked the 3.13
image, which is exactly the job of the control.

Why `--ignore-unfixed`? A CVE with no released fix cannot be remediated by rebuilding.
Failing on it would block every release without improving security. Those findings
remain visible in the informational report and are re-evaluated on every run.

Reproduce locally:

```bash
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 stockpilot-backend:local
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 stockpilot-frontend:local
```

Container scanning is **one** layer. It does not find bugs in our own code (SAST),
leaked secrets, or runtime attacks. The table below shows the other layers.

## Controls in this project

| Layer | Control | Where |
|-------|---------|-------|
| Code quality / static analysis | ruff (incl. flake8-bugbear rules) fails the build | `ci-cd.yml` → `backend-test` |
| Dependencies | exact version pins + lockfiles (`requirements.txt`, `package-lock.json`, `.terraform.lock.hcl`); `npm audit` reports 0 vulnerabilities | `backend/`, `frontend/`, `terraform/` |
| Container images | Trivy gate on HIGH/CRITICAL; minimal multi-stage images; no build tools at runtime | `ci-cd.yml` → `build-scan-push` |
| Supply chain (CI) | every third-party action pinned to a **commit SHA**. In March 2026 attackers force-pushed 76 of 77 `aquasecurity/trivy-action` tags to credential-stealing code; a SHA pin is immune to that. The Trivy binary version is pinned too | `ci-cd.yml` |
| CI permissions | `permissions: contents: read` by default; `packages: write` only for the push job; `id-token: write` only for deploy | `ci-cd.yml` |
| Cloud credentials | GitHub OIDC → short-lived AWS credentials; role trusts only `repo:<owner>/<repo>:ref:refs/heads/main`; no AWS keys stored anywhere | `terraform/github-oidc.tf` |
| Secrets | `.env`, `terraform.tfvars`, `*.tfstate`, kubeconfigs git-ignored; DB password generated by Helm (`randAlphaNum`), stored in a Kubernetes Secret, preserved on upgrade | `.gitignore`, `helm/.../secret.yaml` |
| Workload hardening | non-root UIDs, `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, all capabilities dropped, `RuntimeDefault` seccomp | Dockerfiles, chart templates |
| Cluster policy | namespace enforces the **restricted** Pod Security Standard; non-compliant pods are rejected | `k8s/namespace.yaml` |
| Data at rest | EBS volumes encrypted (gp3 StorageClass); EKS secrets envelope-encrypted with KMS (module default) | `k8s/eks-storageclass-gp3.yaml`, `terraform/eks.tf` |
| HTTP | `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `server_tokens off`; strict request validation (Pydantic, `extra="forbid"`) | `frontend/nginx/`, `backend/app/schemas.py` |

## Known limitations (deliberate, for a classroom environment)

* The app has **no user authentication**. A real deployment would put it behind SSO / an auth proxy.
* Traffic is plain HTTP. Add TLS via the Ingress `tls:` block (e.g. cert-manager + Let's Encrypt) when a domain is used.
* The EKS API endpoint is public, for convenience; restrict `endpoint_public_access_cidrs` in production.
* The GitHub deploy role uses `AmazonEKSClusterAdminPolicy`; a namespace-scoped policy would be tighter.
